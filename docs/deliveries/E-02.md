# E-02 — Modelo de datos y migraciones, propuesta v2
ID: E-02
Nombre: Modelo de datos etapa 1
Objetivo: esquema PostgreSQL multiinstitucional para cognitive y físico básico, con constraints probadas.
Responsable: agente implementador; aprobación Derlis.
Dependencias HARD: E-01 COMPLETED. Gates: GATE-01 aprobado. Dependencias CONTRACT: DATA_MODEL.md y /v1 conservado; no endpoints nuevos. Dependencias EXTERNAL: PostgreSQL aislado y runtime compatible verificado antes de ejecutar.
Alcance: 16 entidades originales y 7 nuevas de etapa 1; documentar esquema por tabla y crear migración Alembic. No conectar cuentas reales ni production. Prueba puede usar PostgreSQL efímero en CI; sin requerir proveedor cloud de negocio.
Exclusiones: grupos/asignaciones, suscripciones, designaciones, IA, endpoints funcionales, Auth integrada y deployment.
Módulos afectados: organizations/rules/catalog/media/training/evaluation/audit; cada modelo pertenece a su módulo.
Archivos previstos: services/api/app/*/models.py; shared/database.py; migrations/env.py y versions; alembic.ini; tests/test_migrations.py; infra/test-postgres.yml; docs/evidence/E-02.
Migraciones: 1 revisión inicial, upgrade/downgrade/upgrade solo DB de prueba; restricciones por tabla/rol; downgrade productivo prohibido sin plan de datos autorizado.
Endpoints: ninguno; salud E-01 no declara conectividad DB.
Permisos: rol migrator separado; runtime sin superusuario/BYPASSRLS; sin acceso cliente a datos de negocio; tests cross-tenant.
Reglas de negocio: ownership personal/institucional; versiones; FKs compuestas tenant; idempotency scope; publicación referencia aprobación exacta; unidades físicas separadas de score; no reglas oficiales inventadas.
Pruebas: T01 DB vacía upgrade crea 23 tablas de dominio; T02 introspección verifica constraints/FKs/índices previstos; T03 downgrade limpia y nuevo upgrade funciona; T04 fixture A/B referencia de B desde A falla por FK; T05 modalidad equivocada de item falla; T06 segunda membresía usuario/org duplicada falla; T07 segunda posición en session_version falla; T08 medición física con modalidad cognitiva falla; T09 runtime no modifica audit_log ni DDL; T10 metadata/Alembic sin drift; T11 dos conexiones/concurrencia clave idempotency producen una única operación guardada, sin afirmar evaluación funcional.
Criterios de aceptación: todos T01..T11 PASS en PostgreSQL real; fixture runtime vs migrator; sin secretos; regresión CI PASS; alcance/tablas rastreables.
Evidencias: SHA, logs sanitizados, versión PostgreSQL, comandos y manifests; NOT_RUN si no hay DB; SQLite no equivale.
Riesgos: motor PostgreSQL/proveedor aún por verificar; grants/RLS deben diseñarse según acceso real. Plan de reversión: revertir commit y downgrade solo efímero; no datos reales.
Condición de cierre: DoD aplicable y aprobación humana. Estado: IN_REVIEW; gates y HARD aprobados. Casos de PostgreSQL deben pasar antes de cierre.
