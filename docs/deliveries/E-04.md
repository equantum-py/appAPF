## Contrato de eventos

Interfaz interna: AuditService.record(connection, authorized_context, action, resource_type, resource_id, request_id, attributes).
La conexión debe ser la misma transacción de la operación; no abrir ni confirmar una transacción dentro del servicio. authorized_context procede de resolución JWT y permiso de operación por E-03, no del cuerpo HTTP. La interfaz devuelve UUID del evento y nunca el JWT.

Persistencia:
- id: UUID generado en servidor.
- organization_id y actor_user_id: derivados del contexto verificado; actor obligatorio para eventos E-04, aunque la tabla histórica admite NULL.
- created_at: timestamp generado por PostgreSQL; no aceptar fecha arbitraria del cliente.
- action: código exacto de la lista permitida, máximo 100 caracteres.
- details: objeto cerrado con schema_version=1, request_id UUID generado por backend, outcome=SUCCESS, resource_type y resource_id UUID, attributes según acción.
- Rechazar campos desconocidos, tipos incorrectos, acciones desconocidas y JSON serializado UTF-8 mayor a 4096 bytes. No truncar silenciosamente.
- No copiar cuerpos, headers ni claims. No almacenar correo, contraseña, JWT, cookie, clave, URL firmada, respuesta del árbitro, rúbrica, criterio ni evaluación detallada. No admitir texto libre en attributes.
- resource_type se valida contra action. No FK genérica: el módulo llamador valida existencia, organización y autorización del recurso antes de record.
- Una llamada autorizada completada genera un evento. Una nueva petición, aunque sea repetición del cliente, es un acceso nuevo: no prometer deduplicación por request_id ni exactly-once distribuido.

## Permisos y operación

Permisos: Todas las decisiones usan DB y membresía activa por petición; user_metadata/app_metadata no conceden roles. Cliente sin credenciales SQL.

| Actor y espacio | Consulta de eventos | Inserción por backend |
|---|---|---|
| ADMIN activo de institución A | Solo A | Solo operación autorizada en A |
| REFEREE, INSTRUCTOR o REVIEWER de A | 403 para listado completo | Solo operación autorizada; nunca envío libre de eventos |
| Dueño de espacio PERSONAL con membresía activa | Solo su espacio personal | Solo operación propia autorizada |
| Administrador/instructor institucional respecto de espacio personal ajeno | 403 | Prohibida |
| Usuario de otra organización o miembro desactivado | 403 | Prohibida |
| Anónimo o JWT inválido | 401 | No evento de negocio |
| Runtime SQL apf_runtime | RLS en contexto validado por API | INSERT; sin UPDATE, DELETE, TRUNCATE ni bypass |

La tabla RLS es defensa adicional: el permiso de lectura administrativa debe verificarse en FastAPI antes de SELECT. No interpretar SELECT SQL como autorización para un rol de negocio. No otorgar nuevas credenciales SQL ni permisos públicos. Las denegaciones no crean eventos en la organización indicada por un atacante.

Reglas de negocio:
1. Verificar identidad, actor, membresía, espacio y permiso de operación; después consultar o modificar el recurso y registrar evento.
2. Para futuras escrituras, mutación y evento en una transacción: error de auditoría revierte ambos. En E-04, fallo de inserción en lectura sensible devuelve 503 sin entregar datos.
3. No persistir eventos SUCCESS de una transacción que se revierte. No insertar eventos tras responder al cliente.
4. Contexto app.subject/app.actor_id/app.organization_id local a transacción; conexiones reutilizadas no heredan tenant.
5. Logs operativos sanitizados pueden indicar request_id/código de error; no bearer, claims, SQL con valores, cuerpos ni secretos.
6. No se declaran intentos fallidos durables ni integridad criptográfica frente al dueño/superusuario DB. Inmutabilidad se garantiza frente al usuario de aplicación.
7. Consulta de auditoría obtiene la página, inserta audit.events.read y confirma antes de responder. Ese evento no aparece en la página ya obtenida; no llamar de nuevo al endpoint para auditarse y evitar recursión.

## HTTP y respuestas

Endpoints:
- Existente GET /v1/organizations/{organization_id}/memberships: conservar payload y permisos E-03; generar organization.memberships.read con returned_count.
- Nuevo GET /v1/organizations/{organization_id}/audit-events: JWT obligatorio; ADMIN institucional o dueño de PERSONAL, siempre membresía activa. Sin POST/PATCH/PUT/DELETE de auditoría.
- Query: limit entero 1..100 (default 50), action opcional de catálogo, from y until opcionales RFC3339 con zona (from inclusivo, until exclusivo; from < until si ambos); before_at RFC3339 y before_id UUID, ambos juntos o ninguno.
- Orden: created_at DESC, id DESC; página siguiente filtra estrictamente por tupla menor a (before_at,before_id). Combinar filtros con organization_id autorizado; nunca aceptar organización/actor dentro del cursor.
- Respuesta 200: {items: [{id, organization_id, created_at, actor_user_id, action, details}], next_cursor: null | {before_at, before_id}}. Obtener limit+1 para detectar página siguiente. details retorna solo formato permitido; filas históricas con JSON fuera de contrato se proyectan a campos permitidos, nunca se exponen valores crudos desconocidos.
- 401 identidad ausente/inválida; 403 actor sin permiso o membresía; 422 filtros/UUID/tipos inválidos; 503 configuración/DB/auditoría no disponibles. ErrorEnvelope y request_id del backend según E-03. Cache-Control: no-store en respuestas. No SW ni cache offline.
- OpenAPI debe declarar campos, límites, formatos, permisos y errores. Consulta paginada sin garantía de snapshot global entre llamadas; no modifica historial previo.
